3. SECURITY - READ BEFORE CUTOVER
================================================================================

3.1 HIGH - 42 of 43 public tables are fully readable and writable by "anon"
    The anon key ships inside the browser bundle, so "anon" means "anyone on the
    internet". Measured on NEW with has_table_privilege:
      tables anon can read or write : 42 of 43
      tables fully locked to anon   :  1  (push_subscriptions)
    30 of them have Row Level Security DISABLED entirely, so all data is exposed
    with no policy check at all: letters, claims, notifications, support_requests,
    public_feedback, letter_templates, letter_movements, service_requests,
    salary_requests, executive archives, and more.

3.2 CRITICAL - the users table, including password hashes
    users has RLS enabled but carries this policy, taken from the project SQL:
      CREATE POLICY "anon_manage_users" ON public.users FOR ALL TO anon
    FOR ALL means SELECT, INSERT, UPDATE and DELETE for the anonymous role.
    Verified: anon can select, insert, update and delete on public.users.
    A single unauthenticated REST call can therefore read all 8 usernames and
    their password hashes, and an attacker can rewrite them.
    This is inherited from the project's own SQL and exists on OLD as well; the
    migration did not introduce it. It is not something to fix blindly, because
    the app authenticates by querying this very table with the anon key, so
    locking it down also locks out login. This needs a deliberate decision:
    move authentication to Supabase Auth, or accept the exposure knowingly.

3.3 Credentials that were pasted into this conversation
    A Supabase personal access token and an sb_secret_ service key were posted
    in chat. Neither is stored in this repository, and the secret key was never
    used. Revoke both and re-issue before cutover. The OLD personal access token
    is still on disk at ~/.supabase/access-token.old-backup and should be revoked
    too once the migration is signed off.

3.4 MEDIUM - .env was committed to git, so the OLD anon key is in history
    .env is tracked in HEAD and appears in at least 5 commits. It exposed
    VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY, VITE_VAPID_PUBLIC_KEY and
    VITE_MESH_CENTRAL_URL. The anon key is not a secret in Supabase's model, but
    combined with 3.1 and 3.2 that key is close to full read/write access to OLD,
    and it is in the history permanently.
    The file is now untracked and staged for deletion, and .env is gitignored, so
    no future commit will carry it. The key itself should be regenerated from the
    Supabase dashboard. History rewriting was NOT attempted - that is a decision
    for you, and it would rewrite commits other people may depend on.
